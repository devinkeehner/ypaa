# Registration check and assistance

In the Puck visual builder, drag **Registration check + help** from Home page into a page. It also works in row, section, card and tab element slots. Heading and introduction are editable. Payload layout and Puck builderData both persist the block. The form is inert while editing. No existing public page is changed automatically.

The same-origin POST `/api/registration-check` looks up the actual attendee's email in `attendees`. It trims and lowercases input and accepts only exact normalized matches after the Mongo adapter's case-insensitive candidate search. It does not match purchaser/contact-only records, unassigned entitlements, breakfast or merchandise purchases. `paid` and `recorded` roster records can confirm; pending, cancelled, refunded, disputed and voided records cannot. Any linked checkout must still be paid/recorded and a linked entitlement must be assigned/redeemed to this attendee. Pooled scholarship seats require active funded contributions. A manually confirmed roster record without legacy links can still confirm. Stripe creates records only after `payment_status=paid`; authorized cash checkout records use `recorded`. No new checkout status fields are introduced.

Each request sends a short result using the existing Resend transport, `RESEND_API_KEY`, `SCHOLARSHIP_FROM_EMAIL`, and confirmation email style. The private lookup email lists every confirmed matching registration by attendee name and confirmation status, including separate registrations sharing an email. It sends one message per request, never one per registration. Payer details, payment identifiers, inactive registrations and other email addresses are omitted; names are escaped in HTML. Requests with more than 100 candidate records fail closed without emailing a partial result. A no-match email explicitly discourages paying again and directs the person to help. Both results produce identical public JSON and page status. Database/provider failures produce a generic 503 for either case. Lookup does not change registration records.

## Abuse controls and configuration

- Mongo-backed atomic limits persist across instances/restarts: one request per email and mode per ten minutes, ten attempts per IP per hour, and 200 attempts globally per hour. The raw private `_registration_check_limits` collection contains HMAC digests, counters and expiry dates, not plain email/IP. A TTL index expires rows. DB/index errors fail closed. A successful duplicate returns the same generic acknowledgement without another send; unsuccessful delivery releases the claim for retry. Resend idempotency keys suppress uncertain provider retries within a ten-minute window.
- Vercel uses its `x-vercel-forwarded-for` ingress header (see [Vercel request headers](https://vercel.com/docs/headers/request-headers)). Other deployments must explicitly set `REGISTRATION_CHECK_TRUST_PROXY=true` only behind an ingress that overwrites `X-Forwarded-For`. Otherwise requests share a conservative IP limit; forged browser headers do not create new IP allowances.
- Same-origin JSON only, no-store responses, 4 KiB streamed body cap, email/name/details limits, honeypot and minimum 1.5 second form age. These controls do not claim that a honeypot proves humanity. Persistent limits bound email abuse.
- `REGISTRATION_CHECK_ORIGIN` can be the exact trusted browser origin if the reverse proxy reconstructs a different request origin (for example `https://necypaact.com`, with no trailing slash). If omitted the API uses the request URL origin. Local runner sets `http://127.0.0.1:3029`; it never trusts an arbitrary Host header to bypass the origin boundary.
- Use a stable configured `PAYLOAD_SECRET` for HMAC keys. Mongo credentials need permission to create the TTL index; provision it in advance if runtime index creation is restricted.

## Organizer assistance

There is no generic stored form/submission collection in the current app; InlineForm and campaign alternatives are HTML forms. This feature therefore adds a private **Registration Help Requests** collection with name, reachable email, short explanation, status and notification status. It does not insert/change CRM contacts or attendees. Only authorized registration staff/admins can read or manage it.

In **More → Notification Recipients**, explicitly assign active verified organizer addresses to **Registration help requested**. Existing scholarship/merchandise recipients are not assumed to handle registration assistance. No live destination was read or changed during development; this new trigger needs committee assignment before release. If no active destination or email sender is configured, help returns a generic unavailable response, logs the specific configuration code, and does not pretend a request was routed. Organizer email failures retain the submitted request with `notificationStatus=pending` for staff follow-up. Staff should monitor that queue, contact the requester through verified channels, and resolve/remove records under the committee's retention policy. There is no automatic background retry worker in this feature.

## Repeatable isolated local tests (Linux / Omarchy)

The runner never loads `.env.local`, reads an existing registration database, copies production data or sends real email. It forces a loopback Mongo URI, synthetic Resend credentials/sender, storage/MCP disabled and payment/integration credentials empty. Test recipients use `@example.invalid`. Capture mode refuses production, non-test database names and non-synthetic addresses before any provider fetch. Keep captured files/screenshots uncommitted in `.local-registration/`.

1. `npm ci --ignore-scripts`
2. `npm run registration:local -- mongo` in a terminal. If `mongod` is not on PATH, set `MONGOD_PATH` to an installed MongoDB binary. On this machine the verified existing binary is `.local-crm/mongodb-binaries/mongod-x64-omarchy-8.0.13`. The command starts a **new** data directory `.local-registration/mongo`, replica set `ypaaTest`, bound only to `127.0.0.1:27029`. Leave it running; stop with Ctrl-C when finished. Do not point this command at another project's data directory.
3. `npm run registration:local -- reset` initializes the verified test replica set and seeds only `ypaa_registration_test`. It refuses to drop a nonempty database without the synthetic marker. `seed` is idempotent; `reset` recreates fixtures and clears captured mail. Neither resets any other database.
4. `npm run test:registration` runs real MongoDB/Payload/HTTP-handler tests in a fresh `ypaa_registration_test_<uuid>` database and deletes that test DB afterward. Mail is captured or fetch is mocked, never sent. Run sequentially with browser tests because both use the local capture file.
5. `npm run registration:local -- dev` starts `http://127.0.0.1:3029`. Visit `/registration-check-test`. Seeded addresses: `paid@example.invalid`, `cash@example.invalid`, `pending@example.invalid`, `refunded@example.invalid`, `cancelled@example.invalid`; use `missing@example.invalid` for no match and `payer@example.invalid` to check that payer-only does not confirm. Organizer is `organizer@example.invalid`. Messages append to `.local-registration/mail.ndjson`.
6. Install Chromium once with `npx playwright install chromium`, or on this Omarchy host use `PLAYWRIGHT_CHROMIUM_PATH=/usr/bin/chromium npm run test:registration:browser`. The browser command checks validation, duplicate clicks, positive/negative results, help persistence/recipient, injected failure/retry, labels/live regions, runtime errors and 1280×900/390×844 layouts. Screenshots: `.local-registration/desktop.png` and `mobile.png`. Browser plugin was unavailable; regular Playwright is the repeatable runner. `PLAYWRIGHT_MODULE_PATH` can optionally select a preinstalled Playwright `index.mjs`.
7. `npm run lint:registration`, `npx tsc --noEmit`, and `npm run lint`. The repo's general ESLint config currently has no TS/React rules; the scoped config actually applies Next/TypeScript/React rules to this feature without changing unrelated lint policy.
8. Stop the dev server, then `npm run registration:local -- build`, followed by `node --test tests/*.test.mjs`. This verifies the normal production build against the isolated DB with capture disabled (no sends occur during a build) and its generated deployment manifest.

The reusable pattern is a per-app loopback endpoint/data directory, explicit synthetic database marker and guarded reset, deterministic Payload seeds through real hooks, captured transport, disposable integration DBs and browser interactions. Future website work can adopt it after inspecting each app's actual datastore and transport. Other website repositories were left untouched in this task.
